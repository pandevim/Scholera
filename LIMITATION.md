## Honest Limitations

**Verifier limitation.** The verifier itself can be wrong — a 4B model occasionally judges "YES" on partial matches. This system reduces hallucinations, it does not eliminate them. The tiered handler limits the blast radius of any single verifier mistake, but the only way to get to zero is to refuse far more aggressively than would be useful.

- **Diagram fidelity is VLM-quality, not true visual reasoning.** If the VLM caption misses a subtle label on a figure, that detail is lost downstream. Adding a "go look at the original page image" tool to the generator would fix this — not built yet.
- **Formula-heavy pages depend on the VLM's LaTeX accuracy.** Dense math derivations occasionally get truncated or paraphrased. A specialized model (Nougat, GOT-OCR) would do better on pure equation pages but adds pipeline complexity.
- **No conversational memory.** Each query is independent. Multi-turn follow-ups would need session state on top of the retrieval layer.
- **Single course at a time.** The retrieval index is built per course. Cross-course queries aren't supported by design — a different system.
- **VLM-on-every-page is brute force.** At this corpus size and with H100-class compute, ingestion is a one-time ~1 hour cost and the simplicity of a single-model pipeline is worth it. At production scale (hundreds of courses, daily uploads from professors), this becomes wasteful — most slides are plain text and don't need a 27B vision model. The right architecture there is a router: cheap heuristics on each page (text density, presence of figures, equation regions from a layout detector) decide whether to send it to PyMuPDF text extraction or to the VLM. Skipped here as a deliberate trade-off, not an oversight.
- **What breaks first at 10× scale.** Embedding storage is fine (FAISS scales). The bottleneck shifts to **rerank latency** — Qwen3-Reranker-8B at ~5s on 50 candidates becomes painful as candidate set grows. Path forward: drop to Qwen3-Reranker-4B (2× faster, small accuracy cost) or migrate to a real vector DB (LanceDB, Qdrant) with batched async reranking.
- **Single-model pipeline option.** Since Qwen3.6-35B-A3B is itself a VLM, in principle one model could serve both ingestion and generation roles, saving load cost. Kept separate here for clarity (different prompts, different concerns) and because the 27B dense model is stronger on document extraction than the 35B MoE. Worth measuring on a future iteration.
- **Prose chunker depends on the embedder's tokenizer being injected.** `chunk_prose` packs paragraphs to a token target using a `count_tokens` callable. The default approximation (`words × 1.3`) undercounts on math- and code-heavy text by 1.3–1.7×, so chunks built with the default can exceed the embedder's context window and silently truncate at encode time — the tail of the chunk becomes unsearchable. The fix is to pass the embedder's actual tokenizer from `ingest.py`; the chunker is correct, but it trusts its caller. Worth a runtime assertion later that validates every chunk fits the embedder's max sequence length.
- **Build-animation slides: dedup turned out to be a no-op at 300 DPI.** Academic decks routinely use click-by-click reveals where each click renders as a separate PDF page (originally visible at 200 DPI as L4=143 chunks and L5=109 — disproportionate to conceptual content, with build pages producing near-identical VLM markdown). We added `chunking.dedupe_build_animations` to drop chunks whose text is ≥0.9 SequenceMatcher-similar to the next chunk in the same doc. **At 300 DPI the function runs but rarely fires** — the higher resolution lets the VLM describe figure details, captions, and layout with enough specificity that consecutive build-animation pages produce meaningfully different markdown. Empirically the known build pairs (L6_S26↔S27, L6_S48↔S49, L4_S71↔S72) have similarity ratios around 0.15–0.23 at 300 DPI, far below the 0.9 threshold. Pairs above 0.7 turn out to be legitimate consecutive slides on the same topic, not duplicates — lowering the threshold would drop real content. **Conclusion:** the DPI bump solved the build-animation problem upstream at the extraction layer; the dedup function is kept as a safety net for future runs at lower DPI but is not load-bearing at 300 DPI. Threshold remains 0.9; chunk count stays at the natural ~860 for this corpus. Configurable via `DEDUPE_ANIMATION_THRESHOLD` if a future corpus needs it.
- **Sentence-window expansion poisons citation anchors; default is now `window=0`.** With `window=1` (the README's design intent), each chunk's text in the generator's prompt is `prev + matched + next` concatenated under a single `[chunk_id]` header. When the fact lives on slide N+1 but the matched chunk is N, the formula appears under N's header and the generator cites N — even though N's *raw* text doesn't contain the fact. The verifier (which checks the matched chunk's raw text, by design) then correctly rejects it. We saw this end-to-end on "What is the formula for scaled dot-product attention?": the formula slide L6_S27 was retrieved at rank #10, but the generator cited adjacent slides L6_S26 / L6_S28 because the formula appeared in *their* windowed context too. Switching to `window=0` made the same query pass with all-YES verdicts. The proper fix is to label sub-slides inside windowed text in the prompt (`----- previous -----` / `----- matched -----` / `----- next -----`) and instruct the generator to cite the slide where the fact actually appears; not yet implemented, so default off.
- **Verifier in production: the strip-smooth tier is the most common outcome, not refusal.** Generators (especially smaller ones) routinely volunteer adjacent-topic trivia and slap a citation on whatever chunk happens to be in the prompt that's topically nearby. Concrete case observed: on "What's the late submission policy?" the generator wrote the correct 10%/20%/0% schedule (cited to L1_S13, all YES) plus a hallucinated sentence — *"any typo or formatting issue in the final report will result in one mark being deducted per occurrence [final_report_rubrics_C1]"* — citing a chunk whose actual text is just the Stevens department address header. The verifier flagged that sentence as NO; the strip-smooth tier dropped it; the user got the correct policy without the fabrication. This is the system working as designed: cheap refusal would have been worse, and the README's tiered handler is what makes that distinction.
- **Rerank order: window-expand BEFORE rerank, not after.** The intuitive optimization is to rerank on each chunk's raw text and only window-expand the top-N winners — cleaner per-chunk relevance signal, smaller batches. We tried it; it regressed on diagram-heavy slides. A bare attention diagram or a vanishing-gradient figure has sparse text on its own page; without window context (the prose on the previous and next slide), the cross-encoder can't tell "this slide is *about* X" from "this slide is *near* X" and lets thematically adjacent but topically wrong slides win (in our smoke test, a slide on *exploding* gradient took rank 1 on a *vanishing* gradient query). The hypothetical motivation for rerank-first — silent truncation of long windowed inputs — doesn't apply to Qwen3-Reranker-8B (8K context, our windows are ~600-1500 tokens). Lesson noted in `retrieval.hybrid_retrieve`'s docstring; revisit only if we swap to a reranker with a small context window.
- **BM25 tokenizer treats LaTeX as opaque tokens.** Our `bm25_tokenize` extracts `[a-z0-9]+` runs after lowercasing, so `\frac{\partial L}{\partial w}` shreds into `[frac, partial, l, partial, w]` — the structural meaning of the math is lost from the sparse index. Acceptable in practice because student queries are written in natural language ("the partial derivative of loss with respect to weights"), not raw LaTeX, so BM25 matches against the prose surrounding equations rather than the equations themselves. Dense retrieval carries the load on formula-driven queries via the embedder's understanding of math vocabulary. If we ever want true sparse formula matching, the fix is to preprocess `$...$` and `$$...$$` blocks into normalized opaque tokens (e.g. hash them and emit a single token per equation) before BM25 tokenization.
